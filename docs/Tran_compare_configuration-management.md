# Task 1: So sánh các công cụ Configuration Management

Các công cụ dưới đây giúp tự động cài đặt phần mềm, quản lý file và dịch vụ, đưa máy về cấu hình mong muốn.

| Công cụ | Agent / Agentless | Push / Pull | Ngôn ngữ viết cấu hình | Tài nguyên | Bảo mật | Độ khó | Khả năng mở rộng |
|---|---|---|---|---|---|---|---|
| **Ansible** | **Agentless**: không cần cài Ansible agent trên máy đích. Với Linux, thường dùng SSH và cần Python để chạy module. | Chủ yếu **push**: Control Node chủ động kết nối và thực hiện task. Có `ansible-pull` cho mô hình pull. | **YAML** cho Playbook; **Jinja2** cho template. Module thường viết bằng Python. | Không có agent thường trực trên máy đích. Khi chạy, module vẫn dùng CPU/RAM; Control Node chịu tải điều phối và các kết nối song song. | SSH mã hóa kết nối; xác thực bằng key hoặc password. Dùng `become` để nâng quyền; Ansible Vault mã hóa dữ liệu nhạy cảm khi lưu trữ. | Tương đối dễ bắt đầu với YAML và SSH. Cần học thêm biến, Role và quản lý quyền khi dự án lớn. | Quản lý được nhiều máy; cần điều chỉnh số tác vụ song song, chia nhóm máy và bố trí bộ điều khiển phù hợp khi quy mô tăng. |
| **Puppet** | Thông thường **có agent**: Puppet agent được cài trên máy đích. Có chế độ chạy cục bộ bằng `puppet apply`. | Chủ yếu **pull**: agent định kỳ lấy catalog cấu hình từ Puppet Server rồi áp dụng. | **Puppet DSL**, mang tính khai báo; file manifest có đuôi `.pp`. | Máy đích dùng tài nguyên cho agent. Puppet Server cần tài nguyên để biên dịch catalog; có thêm thành phần quản lý tùy triển khai. | Agent và server giao tiếp qua HTTPS, xác thực hai chiều bằng chứng chỉ. Cần quản lý CA và chứng chỉ của các máy. | Cần học DSL, resource, catalog và cơ chế chứng chỉ; thường mất công thiết lập ban đầu hơn Ansible. | Phù hợp duy trì cấu hình định kỳ trên nhiều máy. Có thể phân phối tải biên dịch catalog; cần thiết kế và cấp tài nguyên cho server. |
| **Chef Infra** | Mô hình truyền thống **có agent**: Chef Infra Client được cài trên máy đích. | Chủ yếu **pull**: client lấy policy/cookbook từ Chef Infra Server rồi áp dụng theo lịch chạy được cấu hình. | Chủ yếu **Ruby DSL** cho recipe và cookbook. | Máy đích cần Chef Infra Client và Ruby runtime đi kèm. Hệ thống tập trung cần tài nguyên cho Chef Infra Server. | HTTPS bảo vệ đường truyền; client ký yêu cầu API bằng private key để xác thực với server. Cần bảo vệ key và kiểm tra chứng chỉ TLS. | Cần học Ruby DSL, cookbook, recipe và quy trình client/server; tương đối nhiều khái niệm với người mới. | Phù hợp quản lý cấu hình trên nhiều node qua các lượt chạy client. Cần phân bố lịch chạy và cấp tài nguyên cho server theo tải. |
| **SaltStack (Salt)** | Thông thường **có agent** `salt-minion`; **Salt SSH** là lựa chọn agentless. | Master có thể **push** công việc đến minion. Minion cũng có thể chạy state theo lịch và lấy dữ liệu từ master. Salt SSH thực hiện công việc qua SSH. | Thường **YAML + Jinja2** cho state file `.sls`; module mở rộng thường viết bằng Python. | Mô hình agent dùng tài nguyên cho master và minion thường trực. Salt SSH không cần minion thường trực nhưng có chi phí kết nối và thực thi qua SSH. | Mô hình master/minion dùng xác thực bằng key và mã hóa thông điệp. Salt SSH dùng bảo mật SSH. Cần kiểm tra và phê duyệt đúng key của minion. | Cần hiểu master/minion, state, pillar và cơ chế sự kiện; độ phức tạp tăng khi dùng điều phối nâng cao. | Hỗ trợ thực thi trên nhiều minion qua cơ chế thông điệp bất đồng bộ; có kiến trúc phân tầng như syndic. Salt SSH có đặc điểm hiệu năng khác mô hình minion. |

**Ghi chú:** Agent/agentless mô tả việc có cài agent của công cụ trên máy đích hay không; push/pull mô tả bên chủ động thực hiện hoặc lấy công việc. Hai tiêu chí này không đồng nghĩa. Bảng tập trung vào mô hình phổ biến, không liệt kê mọi chế độ hoặc sản phẩm bổ sung.

Nhận xét về tài nguyên, độ khó và khả năng mở rộng là đánh giá định tính theo kiến trúc, không phải kết quả benchmark. Mức sử dụng thực tế phụ thuộc số máy, số task, lịch chạy và cấu hình triển khai. Không thể kết luận công cụ nào an toàn hơn chỉ dựa vào việc có agent hay không.
